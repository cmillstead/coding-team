# C29

| ID | Pattern | Check before dispatch |
|----|---------|----------------------|
| C29 | `@tags: vacuous-assertion; reasoning-shape; scope:both` **A test asserts a property that holds both BEFORE and AFTER the change under test — it pins the half of the behavior that already worked, so it passes whether or not the bug is fixed and verifies nothing new.** Three recurring shapes: (1) asserting CONTAINMENT ("the output includes X") where the requirement is actually about PROVENANCE (X must come from a specific source, not merely appear from anywhere); (2) asserting a TREND or DIRECTION ("the value moved up/down") where the requirement is about SELECTION (which specific item was chosen, not merely that some ordering shifted); (3) asserting a SEMANTIC CLASS ("the result is an error/warning") where the requirement names a SPECIFIC LABEL (a particular error code or field, not merely membership in the class). In each shape the loose assertion is satisfied by both the correct implementation and the plausible wrong one, so a reviewer reading only the test cannot tell which behavior it actually guards. | For every new or modified test in the diff, name the ONE behavior it is meant to guard, then ask: would this exact assertion still pass under the specific wrong behavior the test claims to prevent? If yes, the assertion is vacuous — tighten it to the value, source, or label the requirement actually names. |

**Design default:** Before writing the assertion, state the specific wrong behavior the test must reject and
confirm the assertion actually fails when that wrong behavior is substituted in; then assert
the exact value, source, or label the requirement names — never a looser property
(containment, trend, or class membership) that the pre-change code already satisfies.
