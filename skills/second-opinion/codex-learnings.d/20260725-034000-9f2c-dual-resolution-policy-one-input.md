# C28

| ID | Pattern | Check before dispatch |
|----|---------|----------------------|
| C28 | `@tags: dual-resolution-policy; reasoning-shape; scope:both` **A plan changes how one value is DERIVED in one component (resolved-vs-lexical path, file-scoped-vs-process-scoped root, cached-vs-fresh), while a sibling consumer or a documented contract elsewhere still assumes the OLD derivation.** The change reads as locally correct — each component is internally consistent — but the two policies meet at one input and disagree, producing either an exploitable gap or a silent regression. Caught twice in one plan (`2026-07-25-write-guard-reachability`): (1) Task 1 required `is_orchestrator_file()` to match LEXICALLY while Task 2 required resolving the target for ownership; a symlink `/tmp/alias -> /repo` then let ownership find the armed plan while spelling classified the path as external scratch, exempting it — gate off. (2) The same task moved root derivation from process-scoped `git rev-parse` to a walk up to the nearest `docs/plans/` ancestor, silently REGRESSING an explicit docstring contract at `_lib/active_plan.py:25-28` ("Worktrees and the primary checkout resolve to the same root") — a linked worktree has no `docs/plans/` of its own, so the walk found nothing and the gate went dormant. Both were invisible in a same-model review because each component was correct in isolation. | For every value whose DERIVATION the plan changes, do two greps before dispatch. (a) **All other readers**: grep for every call site and consumer of that value; for each, ask which derivation policy it assumes and whether the plan updates it. (b) **Contracts asserting the old behavior**: grep docstrings, module headers, comments and adjacent plans for prose stating the current guarantee — a documented invariant that the change falsifies is a REGRESSION, not a gap, and it will not show up as a failing test if no test covers the interaction. When two components must answer different questions about the same input (how was it SPELLED vs. what OWNS it), say so explicitly in the plan and route each question to its own input — never let one resolution policy leak across the boundary. |

**Design default:** When a plan changes how a value is derived, enumerate every consumer of that value and every written contract asserting its old behavior, and state per consumer which policy it uses. If two consumers need different policies for the same input, split the inputs by question rather than picking one policy globally.
